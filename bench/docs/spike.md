## S2: management API authentication

- Open-source v2.5.1 installs `SetupLockMiddleware` in front of `/api` while dashboard auth is not active (`transports/bifrost-http/server/server.go:3745-3750`). Every non-whitelisted `/api` call needs header `X-Bifrost-Setup-Token` (`handlers/middlewares.go:1875`, check at `:1961-2010`). Missing header: 401; wrong token: 403; no token configured at all: 403 for every call, forever.
- The token is operator-provisioned: `setup_token` in `config.json` (accepts `env.NAME`) or env `BIFROST_SETUP_TOKEN` (`lib/config.go:7388-7395`). It is never persisted. `run.sh` generates one per run into `out/setup-token` and passes it to compose through `out/spike.env`.
- Once an admin account exists and dashboard auth is on, the setup token stops working and session or Basic auth applies (`middlewares.go:1951-1959`). Not needed for the bench: keep auth off and hold the setup token.
- Not tested: creating the admin account (`PUT /api/config` with `auth_config.setup_token`, per the boot log).

- **Join key (conversation rows):** the slot (`selected_key_name` = ledger `slot`, one slot per run) plus the upstream `msg_` id. The row keeps it only in `raw_response` (detail row), and only when the provider has `store_raw_request_response: true`; for streams `raw_response` holds every upstream SSE `data:` payload in order, separated by blank lines, and the first one (`message_start`) carries `message.id`. `responses_output[].id` is a Bifrost-generated id, not the upstream one. Failed rows carry the proxy's nonce in `raw_response` and `error_details.error.message`.
- **Attempts:** `sha256(raw_request)` equals the proxy's `req_sha256` byte for byte, so all attempts of one row share it; the count of such ledger lines equals `len(attempt_trail)` (`attempts_match`).
- **No forwarded id header:** Bifrost sends no request id upstream; its own id (`x-bifrost-request-id` = row `id`) exists only on the client side.
- **count_tokens / models:** client calls through the VK are logged as rows with `object` `count_tokens` and `list_models` (counted: false in the ledger). `count_tokens` joins by body hash. `list_models` has an empty `raw_request`, so it is only joinable by order, and Bifrost's own key-refresh `GET /v1/models` calls hit the proxy with no row at all. Filter on `object` and `path`. The `list_models` row id (`075eeb13-1b38-4f82-806f-118bad36a226`) differs from the `x-bifrost-request-id` header the client got (`64c36d7e-34e9-441f-ad36-b55a2c759902`).
- **Paging:** `GET /api/logs?virtual_key_ids=<vk id>&start_time=<run start>&limit=2&offset=N&order=asc`; default limit 50, max 1000 (`handlers/logging.go:860-897`). Stop at a short page. Without `start_time`/`end_time`, `pagination.total_count` comes from the `mv_logs_hourly` matview and lags (it read 0 with rows present in a manual run); any bounded window under 24 h makes it a raw COUNT (`framework/logstore/matviews.go:1345-1356`, `rdb.go:1330-1346`).

## Design (section 13) corrections

1. **Pinned price file is mandatory, not a nicety (13.5).** Without `file://` datasheets a fresh gateway with no internet exits at boot. Add `mcp_library_sync_interval: 0` and `live_models_sync_interval: 0` to the gateway settings.
2. **Join key (13.4, S5) needs `store_raw_request_response: true` on the provider.** The provider's response id is not a row column; it lives in the detail row's `raw_response`. Without that flag the fallback is order plus usage. Error rows join by the proxy nonce in `raw_response`/`error_details`. Attempts group by `sha256(raw_request)` = ledger `req_sha256`.
3. **No forwarded request id.** Bifrost sends only `anthropic-version`, `content-type`, `content-length`, `user-agent: fasthttp`, `x-api-key` (plus `accept`, `cache-control`, `connection` on streams) upstream. A join via a forwarded header is not possible on stock v2.5.1.
4. **Weight is required on the VK provider config,** or plain model ids do not route (governance skips weightless candidates).
5. **`total_count` is not a completeness signal** without a bounded time window (matview lag). Page to a short page; pass `start_time`.
6. **Uncounted `GET /v1/models` traffic** comes from Bifrost itself on key create and on every provider PUT (2 per key). It has no row. "Every ledger entry matches a row" (13.4 step 2) must be restricted to counted lines plus client `count_tokens`/`models` calls, and a provider PUT mid-run would add proxy traffic.
7. **Management auth (13.2) is the setup token** in `X-Bifrost-Setup-Token`, from `BIFROST_SETUP_TOKEN`; the line range cited in DESIGN section 5 S2 (`server.go:3863-3867`) is `server.go:3745-3750` on the v2.5.1 tag.
8. **Streamed rows keep the whole upstream event sequence** in `raw_response` (with `store_raw_request_response: true`), including `tool_use` blocks and `input_json_delta` frames. S8's gateway-side tool-call count can be rebuilt from detail rows, not only from Claude Code's stream. Error rows have an empty `selected_key_name`/`selected_key_id`; the slot is in `attempt_trail[0].key_name`.
9. **List rows lack `attempt_trail`;** one detail fetch per row is required (confirms 13.4 step 3).
10. **"No row is `processing`" proves nothing on its own.** Rows are written in batches up to 5 s after the response and never showed as `processing`; an early poll sees zero rows and zero `processing`. The stop rule must be ledger-driven (row count and join cover every counted ledger line), and the gateway should set `logs_store.writer.batch_interval` low (for example `"500ms"`, untested).
11. The `list_models` row id may differ from the `x-bifrost-request-id` the client saw (see S5); key `count_tokens`/`list_models` joins on body hash and order, not on that header.
